===TITLE===
Claude Certified Architect – Foundations: руководство по сертификационному экзамену (Exam Guide)
===H1===
Введение
===P===
Сертификация Claude Certified Architect – Foundations подтверждает, что практикующие специалисты способны принимать обоснованные решения о компромиссах при внедрении реальных решений с использованием Claude.
===P===
Данный экзамен проверяет фундаментальные знания в отношении Claude Code, Claude Agent SDK, Claude API и Model Context Protocol (MCP) — основных технологий, применяемых для построения приложений промышленного уровня с Claude.
===P===
Вопросы на этом экзамене опираются на реалистичные сценарии, заимствованные из фактических примеров использования заказчиками, включая: построение агентных систем для поддержки клиентов; проектирование мультиагентных исследовательских пайплайнов; интеграцию Claude Code в рабочие процессы CI/CD; создание инструментов для повышения продуктивности разработчиков; извлечение структурированных данных из неструктурированных документов. Кандидаты должны продемонстрировать не только концептуальные знания, но и практическое суждение об архитектуре, конфигурации и компромиссах в промышленных развёртываниях.
===P===
Настоящее руководство описывает содержание экзамена, перечисляет предметные области и формулировки задач, приводит примеры вопросов и рекомендует стратегии подготовки. Используйте его совместно с практическим опытом для эффективной подготовки.
===H1===
Описание целевого кандидата
===P===
Идеальный кандидат на эту сертификацию — архитектор решений, который проектирует и внедряет промышленные приложения с Claude. У такого кандидата есть практический опыт в следующих областях:
===BULLET===
Построение агентных приложений с использованием Claude Agent SDK, включая мультиагентную оркестрацию, делегирование задач субагентам, интеграцию инструментов и хуки жизненного цикла
===BULLET===
Конфигурирование и настройка Claude Code под командные рабочие процессы с использованием файлов CLAUDE.md, Agent Skills, интеграций MCP-серверов и режима планирования (plan mode)
===BULLET===
Проектирование интерфейсов инструментов и ресурсов Model Context Protocol (MCP) для интеграции с внутренними (backend) системами
===BULLET===
Инженерия промптов, обеспечивающая надёжный структурированный вывод, с опорой на JSON-схемы, few-shot примеры и паттерны извлечения
===BULLET===
Эффективное управление контекстными окнами в условиях длинных документов, многоходовых диалогов и передач контекста между агентами (multi-agent handoffs)
===BULLET===
Интеграция Claude в CI/CD пайплайны для автоматизированного код-ревью, генерации тестов и обратной связи по pull request
===BULLET===
Принятие обоснованных решений по эскалации и надёжности, включая обработку ошибок, рабочие процессы с участием человека в контуре (human-in-the-loop) и паттерны самооценки
===P===
Как правило, такой кандидат имеет не менее шести месяцев практического опыта разработки с использованием Claude API, Agent SDK, Claude Code и MCP и понимает как возможности, так и ограничения больших языковых моделей в промышленных средах.

===H2===
Типы ответов
===P===
Все вопросы на экзамене имеют формат множественного выбора. У каждого вопроса один правильный ответ и три неправильных ответа (дистракторы).
===P===
Выберите единственный ответ, который наилучшим образом завершает утверждение или отвечает на вопрос.
===P===
Дистракторы — это варианты ответов, которые может выбрать кандидат с неполными знаниями или неполным опытом.
===P===
Вопросы, на которые не дан ответ, засчитываются как неверные; за попытки угадать ответ штраф не начисляется.
===H2===
Результаты экзамена
===P===
Экзамен имеет итоговую оценку в виде статуса «сдал» или «не сдал». Оценивание производится относительно минимального стандарта, установленного предметными экспертами.
===P===
Ваши результаты сообщаются в виде масштабированного балла в диапазоне от 100 до 1000. Минимальный проходной балл составляет 720.
===P===
Модели масштабированного оценивания помогают приводить к сопоставимому виду баллы по различным формам экзамена, которые могут незначительно отличаться по уровню сложности.

===H2===
Сценарии экзамена (Exam Scenarios)
===P===
На экзамене используются вопросы, привязанные к сценариям. Каждый сценарий задаёт реалистичный контекст промышленной эксплуатации (production context), в рамках которого формулируется набор вопросов.
===P===
В ходе экзамена вам будут показаны 4 сценария; они выбираются случайным образом из полного набора из шести сценариев, приведённых ниже.
===H2===
Сценарий 1: Агент поддержки клиентов по разрешению обращений (Customer Support Resolution Agent)
===P===
Вы разрабатываете агента для разрешения обращений в поддержку клиентов с использованием Claude Agent SDK. Агент обрабатывает запросы с высокой степенью неоднозначности, такие как возвраты товара, споры по выставлению счетов (billing disputes) и вопросы, связанные с учётной записью (account issues).
===P===
Агент имеет доступ к вашим внутренним системам через пользовательские (custom) инструменты Model Context Protocol (MCP): get_customer, lookup_order, process_refund, escalate_to_human.
===P===
Ваша целевая метрика — разрешение не менее чем в 80% случаев при первом контакте (first-contact resolution), при этом вы должны понимать, в каких ситуациях необходима эскалация.
===P===
Основные предметные области, к которым относится этот сценарий: агентная архитектура и оркестрация (Agentic Architecture & Orchestration); проектирование инструментов и интеграция MCP (Tool Design & MCP Integration); управление контекстом и надёжность (Context Management & Reliability).
===H2===
Сценарий 2: Генерация кода с Claude Code (Code Generation with Claude Code)
===P===
Вы используете Claude Code для ускорения разработки программного обеспечения. Ваша команда применяет его для генерации кода, рефакторинга, отладки и создания документации.
===P===
Вам необходимо интегрировать Claude Code в ваш рабочий процесс разработки с использованием пользовательских slash-команд (custom slash commands), конфигураций CLAUDE.md, а также понимать, когда следует использовать режим планирования (plan mode), а когда — прямое выполнение (direct execution).
===P===
Основные предметные области: настройка Claude Code и рабочие процессы (Claude Code Configuration & Workflows); управление контекстом и надёжность (Context Management & Reliability).
===H2===
Сценарий 3: Мультиагентная исследовательская система (Multi-Agent Research System)
===P===
Вы создаёте мультиагентную исследовательскую систему с использованием Claude Agent SDK. Агент-координатор (coordinator agent) делегирует задачи специализированным субагентам: один выполняет поиск в Интернете, один анализирует документы, один синтезирует полученные выводы, ещё один формирует отчёты.
===P===
Система исследует заданные темы и формирует развёрнутые отчёты с указанием источников (comprehensive, cited reports).
===P===
Основные предметные области: агентная архитектура и оркестрация; проектирование инструментов и интеграция MCP; управление контекстом и надёжность.
===H2===
Сценарий 4: Продуктивность разработчиков с Claude (Developer Productivity with Claude)
===P===
Вы создаёте инструменты для повышения продуктивности разработчиков с использованием Claude Agent SDK. Агент помогает инженерам исследовать незнакомые кодовые базы, разбираться в унаследованных (legacy) системах, генерировать шаблонный код (boilerplate code) и автоматизировать повторяющиеся задачи.
===P===
Агент использует встроенные инструменты (Read, Write, Bash, Grep, Glob) и интегрируется с серверами Model Context Protocol (MCP).
===P===
Основные предметные области: проектирование инструментов и интеграция MCP; настройка Claude Code и рабочие процессы; агентная архитектура и оркестрация.
===H2===
Сценарий 5: Claude Code для непрерывной интеграции (Claude Code for Continuous Integration)
===P===
Вы интегрируете Claude Code в ваш пайплайн непрерывной интеграции и непрерывного развёртывания (Continuous Integration/Continuous Deployment, CI/CD). Система выполняет автоматизированное код-ревью, генерирует тестовые сценарии и предоставляет обратную связь по запросам на включение изменений (pull requests).
===P===
Вам необходимо проектировать промпты так, чтобы обратная связь была практически применимой (actionable), а доля ложных срабатываний (false positives) минимизировалась.
===P===
Основные предметные области: настройка Claude Code и рабочие процессы; промпт-инжиниринг и структурированный вывод (Prompt Engineering & Structured Output).
===H2===
Сценарий 6: Структурированное извлечение данных (Structured Data Extraction)
===P===
Вы создаёте систему структурированного извлечения данных с использованием Claude. Система извлекает информацию из неструктурированных документов, проверяет выходные данные с помощью схем в нотации JavaScript Object Notation (JSON) и поддерживает высокую точность.
===P===
Система должна корректно обрабатывать краевые случаи (edge cases) и интегрироваться с последующими по конвейеру системами (downstream systems).
===P===
Основные предметные области: промпт-инжиниринг и структурированный вывод; управление контекстом и надёжность.

Задача 1.2: Оркестрация мультиагентных систем с паттерном координатор–субагенты
===H3===
Знать:
===BULLET===
Архитектура «звезда»: координатор управляет всей коммуникацией между субагентами, обработкой ошибок и маршрутизацией информации
===BULLET===
Субагенты работают в изолированном контексте — история диалога координатора им не передаётся автоматически
===BULLET===
Роль координатора: декомпозиция задач, делегирование, агрегация результатов, выбор субагентов по сложности запроса
===BULLET===

===BULLET===
Проектировать координаторов, которые анализируют требования и динамически выбирают субагентов, а не всегда гоняют полный пайплайн
===BULLET===
Распределять область исследования между субагентами, минимизируя дублирование (разные подтемы или типы источников)
===BULLET===
Реализовывать итеративное уточнение: координатор оценивает пробелы в синтезе, повторно делегирует поиск и анализ с уточнёнными запросами, снова вызывает синтез до достаточного покрытия
===BULLET===
Направлять всю коммуникацию субагентов через координатора для наблюдаемости, единообразной обработки ошибок и контролируемого потока информации

Задача 1.4: Многошаговые рабочие процессы с принуждением и передачей эстафеты (handoff)

Разница между программным принуждением (хуки, предварительные шлюзы) и подсказками в промпте для порядка шагов

===BULLET===
Формировать структурированные сводки для эскалации к людям (ID клиента, первопричина, сумма возврата, рекомендуемое действие), когда у человека нет доступа к полной транскрипции

Задача 1.7: Управление состоянием сессии, возобновление и fork
===H3===
Знать:
===BULLET===
Именованное возобновление сессии: --resume <session-name> для продолжения конкретного диалога
===BULLET===

Приведённые ниже примеры вопросов иллюстрируют формат и уровень сложности экзамена. Они взяты из практического теста (practice test) и снабжены пояснениями, облегчающими обучение.
===H2===
Сценарий: агент поддержки клиентов по разрешению обращений (Customer Support Resolution Agent)
===P===
Вопрос 1: Данные продакшена показывают, что в 12% случаев ваш агент полностью пропускает вызов get_customer и вызывает lookup_order, используя только имя клиента, указанное в формулировке запроса, что периодически приводит к ошибочной идентификации учётных записей и к неверным возвратам средств. Какое изменение наиболее эффективно устранит эту проблему надёжности?
===P===
A) Добавить программную предпосылку (programmatic prerequisite), которая блокирует вызовы lookup_order и process_refund до тех пор, пока get_customer не вернёт проверенный идентификатор клиента.
===P===
B) Усилить системный промпт, явно указав в нём, что верификация клиента через get_customer является обязательной перед любыми операциями с заказами.
===P===
C) Добавить few-shot примеры, демонстрирующие, что агент всегда сначала вызывает get_customer, даже когда клиенты сами сообщают детали, относящиеся к заказу.
===P===
D) Внедрить классификатор маршрутизации (routing classifier), который анализирует каждый запрос и включает только то подмножество инструментов, которое соответствует данному типу запроса.
===P===
Правильный ответ: A
===P===
Когда для критически важной бизнес-логики требуется определённая последовательность вызовов инструментов (например, подтверждение личности клиента перед обработкой возвратов средств), программное принуждение обеспечивает детерминированные гарантии, которых нельзя достичь подходами, основанными исключительно на тексте промпта.
===P===
Варианты B и C опираются на вероятностное соблюдение ограничений со стороны большой языковой модели (LLM), чего недостаточно в ситуациях, когда ошибки несут финансовые последствия.
===P===
Вариант D касается доступности инструментов, а не порядка их вызова; при этом фактическая проблема, о которой идёт речь, связана именно с порядком вызова инструментов, а не с тем, какие инструменты вообще доступны.
===P===
Вопрос 2: Журналы продакшена показывают, что агент часто вызывает get_customer, когда пользователи задают вопросы о заказах (например: «проверьте мой заказ №12345»), вместо того чтобы вызывать lookup_order. У обоих инструментов минимальные описания («Retrieves customer information» / «Retrieves order details»), и они принимают сходные форматы идентификаторов. Какой наиболее эффективный первый шаг следует предпринять для повышения надёжности выбора инструмента?
===P===
A) Добавить в системный промпт few-shot примеры, демонстрирующие корректные паттерны выбора инструмента, с 5–8 примерами, в которых запросы, связанные с заказами, направляются в lookup_order.
===P===
B) Расширить описание каждого инструмента так, чтобы оно включало форматы входных данных, которые инструмент обрабатывает, примеры запросов, краевые случаи и пояснения границ применения, объясняющие, когда следует использовать данный инструмент по сравнению с похожими инструментами.
===P===
C) Реализовать слой маршрутизации (routing layer), который перед каждым ходом разбирает пользовательский ввод и заранее выбирает подходящий инструмент на основе обнаруженных ключевых слов и шаблонов идентификаторов.
===P===
D) Объединить оба инструмента в один инструмент lookup_entity, который принимает любой идентификатор и внутренне определяет, к какому бэкенду следует обратиться за данными.
===P===
Правильный ответ: B
===P===
Описания инструментов являются основным механизмом, который большие языковые модели используют при выборе инструмента. Когда описания минимальны, моделям не хватает контекста, чтобы различать сходные между собой инструменты.
===P===
Вариант B напрямую устраняет эту первопричину при относительно небольших затратах усилий и при высокой отдаче (low-effort, high-leverage fix).
===P===
Few-shot примеры (вариант A) увеличивают расход токенов, не устраняя при этом лежащую в основе проблему.
===P===
Слой маршрутизации (вариант C) является излишне сложным решением (over-engineered) и обходит способность LLM к пониманию естественного языка.
===P===
Объединение инструментов (вариант D) может быть допустимым архитектурным решением, но требует больших усилий, чем оправдывает формулировка «первый шаг» (first step), когда непосредственная проблема заключается в недостаточности описаний.
===P===
Вопрос 3: Ваш агент достигает 55% показателя разрешения при первом контакте (first-contact resolution), что заметно ниже целевого значения 80%. Журналы показывают, что он эскалирует простые случаи (стандартные возвраты при повреждении товара при наличии фотографических доказательств), при этом пытаясь автономно обрабатывать сложные ситуации, требующие исключений из правил политики. Какой способ наиболее эффективно улучшит калибровку решений об эскалации?
===P===
A) Добавить в системный промпт явные критерии эскалации с few-shot примерами, демонстрирующими, когда следует эскалировать обращение, а когда разрешать его автономно.
===P===
B) Заставить агента перед каждым ответом самооценивать уверенность по шкале от 1 до 10 и автоматически направлять запросы к человеку, когда уверенность падает ниже порога.
===P===
C) Развернуть отдельную модель-классификатор, обученную на исторических тикетах, которая до начала работы основного агента предсказывает, какие запросы требуют эскалации.
===P===
D) Внедрить анализ тональности (sentiment analysis) для оценки уровня фрустрации клиента и автоматически эскалировать обращения, когда «негативная» тональность превышает порог.
===P===
Правильный ответ: A
===P===
Добавление явных критериев эскалации с few-shot примерами напрямую устраняет первопричину: неясные границы принятия решений. Это соразмерный первый шаг до добавления дополнительной инфраструктуры.
===P===
Вариант B не работает, поскольку самооценка уверенности LLM калибруется плохо: агент уже демонстрирует необоснованно высокую уверенность в сложных случаях.
===P===
Вариант C излишне усложняет решение: он требует размеченных данных и инфраструктуры машинного обучения в ситуации, когда оптимизация промпта ещё не предпринималась.
===P===
Вариант D решает совершенно иную проблему: тональность не коррелирует со сложностью кейса, которая в данном описании и является фактической проблемой.

===P===

===P===
Закрепляемые предметные области (Domains reinforced): Область 1 (Agentic Architecture & Orchestration), Область 2 (Tool Design & MCP Integration), Область 5 (Context Management & Reliability).

Упражнение 3: Построение пайплайна структурированного извлечения данных (Build a Structured Data Extraction Pipeline)
===P===
Цель (Objective): отработать проектирование JSON-схем, использование tool_use для структурированного вывода, реализацию циклов «валидация — повтор» (validation-retry loops) и стратегии пакетной обработки.
===P===
Шаги (Steps):
===BULLET===
1. Определите инструмент извлечения с JSON-схемой, содержащей обязательные и необязательные поля, перечисление (enum) с паттерном «"other" + строка с деталями» и полями, допускающими null, для информации, которая может отсутствовать в исходных документах. Обработайте документы, в которых некоторые поля отсутствуют, и убедитесь, что модель возвращает null, а не выдумывает значения.
===BULLET===
2. Реализуйте цикл «валидация — повтор»: при ошибке валидации Pydantic или JSON-схемы отправляйте последующий запрос, включающий документ, неудачное извлечение и конкретное сообщение об ошибке валидации. Отслеживайте, какие ошибки устранимы повтором (несовпадения формата), а какие нет (информация отсутствует в источнике).
===BULLET===
3. Добавьте few-shot примеры, демонстрирующие извлечение из документов с различными форматами (например, встроенные цитаты против библиографий, повествовательные описания против структурированных таблиц), и убедитесь, что обработка структурного разнообразия улучшилась.
===BULLET===
4. Спроектируйте стратегию пакетной обработки: отправьте пакет из 100 документов с использованием Message Batches API, обрабатывайте сбои по custom_id, повторно отправляйте неуспешные документы с модификациями (например, разбиение слишком больших документов на части) и рассчитайте суммарное время обработки относительно ограничений SLA.
===BULLET===
5. Реализуйте стратегию маршрутизации на человеческое ревью: пусть модель выводит оценки уверенности по полям (field-level confidence), направляйте извлечения с низкой уверенностью на проверку человеком и анализируйте точность по типу документа и по полям, чтобы убедиться в согласованной работе на всех сегментах.
===P===
Закрепляемые предметные области: Область 4 (Prompt Engineering & Structured Output), Область 5 (Context Management & Reliability).
===H2===
Упражнение 4: Проектирование и отладка мультиагентного исследовательского пайплайна (Design and Debug a Multi-Agent Research Pipeline)
===P===
Цель (Objective): отработать оркестрацию субагентов, управление передачей контекста, распространение информации об ошибках и синтез с отслеживанием происхождения данных (provenance tracking).
===P===
Шаги (Steps):
===BULLET===
1. Постройте агента-координатора, который делегирует задачи как минимум двум субагентам (например, веб-поиск и анализ документов). Убедитесь, что в allowedTools координатора включено значение "Task" и что каждый субагент получает результаты исследования непосредственно в своём промпте, а не полагается на автоматическое наследование контекста.
===BULLET===
2. Реализуйте параллельное выполнение субагентов, заставив координатора сформировать несколько вызовов инструмента Task в одном ответе. Измерьте улучшение задержки (latency) по сравнению с последовательным выполнением.
===BULLET===
3. Спроектируйте структурированный вывод субагентов, разделяющий содержимое и метаданные: каждая находка должна включать утверждение (claim), выдержку-доказательство (evidence excerpt), URL источника или имя документа и дату публикации. Убедитесь, что субагент синтеза сохраняет атрибуцию источников при объединении находок.
===BULLET===
4. Реализуйте распространение ошибок: смоделируйте тайм-аут субагента и убедитесь, что координатор получает структурированный контекст ошибки (тип сбоя, выполненный запрос, частичные результаты). Проверьте, что координатор может продолжить работу с частичными результатами и аннотировать итоговый вывод указанием пробелов покрытия (coverage gaps).
===BULLET===
5. Протестируйте систему на противоречивых исходных данных (например, два авторитетных источника с разной статистикой) и убедитесь, что вывод синтеза сохраняет оба значения с атрибуцией источников, а не произвольно выбирает одно, и что отчёт структурирован так, чтобы различать хорошо обоснованные и спорные выводы.
===P===
Закрепляемые предметные области: Область 1 (Agentic Architecture & Orchestration), Область 2 (Tool Design & MCP Integration), Область 5 (Context Management & Reliability).

===H2===
Рекомендации по подготовке к экзамену (Exam Preparation Recommendations)
===P===
Чтобы подготовиться к этому сертификационному экзамену:
===P===
1. Соберите агента с использованием Claude Agent SDK: реализуйте полный агентный цикл с вызовом инструментов, обработкой ошибок и управлением сессиями. Потренируйтесь в порождении субагентов и передаче контекста между ними.
===P===
2. Настройте Claude Code для реального проекта: организуйте иерархию CLAUDE.md, создайте правила с привязкой к путям в .claude/rules/, соберите пользовательские навыки с опциями frontmatter (context: fork, allowed-tools) и интегрируйте как минимум один MCP-сервер.
===P===
3. Спроектируйте и протестируйте MCP-инструменты: напишите описания инструментов, которые чётко различают сходные инструменты. Реализуйте структурированные ответы об ошибках с категориями ошибок и флагами возможности повтора. Проверьте надёжность выбора инструмента на неоднозначных запросах.
===P===
4. Постройте пайплайн структурированного извлечения данных: используйте tool_use с JSON-схемами, реализуйте циклы «валидация — повтор», спроектируйте схемы с необязательными и допускающими null полями и попрактикуйтесь в пакетной обработке с Message Batches API.
===P===
5. Потренируйтесь в приёмах промпт-инжиниринга: пишите few-shot примеры для неоднозначных сценариев; формулируйте явные критерии ревью для снижения ложных срабатываний; проектируйте многопроходные архитектуры ревью для крупных код-ревью.
===P===
6. Изучите паттерны управления контекстом: практикуйтесь в извлечении структурированных фактов из объёмных выводов инструментов, в использовании scratchpad-файлов для длинных сессий и в проектировании делегирования субагентам для управления ограничениями контекста.
===P===
7. Повторите паттерны эскалации и участия человека в контуре (human-in-the-loop): разберитесь, когда следует эскалировать (пробелы в политике, запросы клиента, невозможность прогресса) и когда разрешать автономно. Потренируйтесь в проектировании рабочих процессов человеческого ревью с маршрутизацией на основе уверенности.
===P===
8. Пройдите практический экзамен (Practice Exam): перед сдачей настоящего экзамена завершите практический экзамен (ссылка будет предоставлена отдельно). Практический экзамен охватывает те же сценарии и формат вопросов, что и настоящий экзамен, и после каждого ответа показывает пояснения, помогающие закрепить понимание.
